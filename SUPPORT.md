# Support

Use the repository's issue chooser for ordinary support, reproducible non-sensitive defects, and feature requests unless that repository documents a different supported route. There is no organization-wide guaranteed response or resolution time.

Before opening an issue, gather the smallest project and environment information needed to explain the problem. Include clear reproduction steps and the expected and actual result.

Never include private repository or site identities in a public issue or pull request. Replace them with neutral labels and reduce the report to a non-sensitive reproducer. If that is not possible, do not publish the private material.

Do not publish vulnerability details, credentials, tokens, webhook secrets, WordPress salts, database or customer data, signed URLs, private source, non-public release assets, full production logs, private workbench material, Dex identifiers, or other sensitive information in an issue or pull request.

Report vulnerabilities through the private route described in `SECURITY.md`. Reports about conduct belong through the private enforcement route in `CODE_OF_CONDUCT.md`, not through a public issue.

A repository-local `SUPPORT.md` may define its supported versions, diagnostic fields, support scope, or alternate non-sensitive support route while preserving these disclosure-safety requirements.
